## 一、详而分清爽令

所有写入本项目的文本内容，遵循以下排版规则：

### 拆段规则

- 同段超过 3 行连续叙述 → 拆成小标题组或短段组
- 一句话只说一件事
- 禁止用顿号/逗号堆叠 3 个以上并列事实

### 表格化规则

- 3 个以上同类事项 → 转表格或换行列表
- 对比/前后对比类内容 → 必须用表格
- 键值对超过 3 组 → 换行列表或表格

### 长块切分

- 单个连续文本块超过 10 行 → 必须插入小标题或分隔

### 信息量守恒

- 所有排版调整=仅改版式，不删内容
- 详细量不减（宁长勿漏），清晰靠分层不靠删减

## 二、术语自解释令

专业术语/缩写/系统内代号首次在一份文件中出现时：

- 括号内给一句话解释
- 已在同文件早先出现过的不重复解释
- 例：「五腿闸（每个新窗口开工前强制执行的五步检索流程）」

## 三、适用范围

本规范适用于公共库（civ-os）内所有 .md 文件的新增和修改。iterate.py 整合产出的文件也应遵循本规范（system-prompt 可迭代层指针行=配套待办，IMMUTABLE 区不动）。

## 五、自然人可读优先与智能体执行信息分层（#ZZ-CHAT-1016-B）

公共规范可以保留机器可执行的路径、命令和状态码；但给自然人的正文以「没做过 GitHub/迭代引擎的人也能明白」为验收标准。不要把面向主控窗口的交接指令原样当作人的完成报告。

### 术语首次出现要说白话

- `master`：公共库大家共同使用、默认同步的正式版本。
- PR（合并请求）：先放在一边等待合入正式版本的改动单；它还不是正式库里的结果。
- 日切：只适用于没有 GitHub 写权限的窗口——当天先完整记录，第二天开始时再处理已确认内容。
- 远端 SHA：GitHub 当前版本的完整唯一编号，用于确认并发更新和同步位置；首次出现时说明它的用途。

术语可保留给智能体执行，但首次出现必须附简短中文解释。不得让「PR 还开着」「push 成功」「分支已更新」成为唯一的人类可见结论；要明确说正式公共库是否已更新。

### 对话按条目展开，不以状态摘要替代内容

每轮先逐项列出从上下文提取的细节；选一项或一组不可分的细节做完整说明和逻辑分析，其余写入积压列表。每个待确认条目要给出背景、含义、条件/边界、影响、拟修改位置和建议；只有完整展开并给自然人实际反馈机会的条目，才能进入默认生效清单。

已确认条目的报告应写清「改了哪份文件的哪一段、为什么这样处理、目前是否已进入正式公共库」。未展开、待验证、或只写了标题的项目不得用一行模糊状态伪装成已完成。

### 人类主报告与机器同步附注分层

主报告使用自然语言，按「本轮条目 → 本轮完整展开与分析 → 已确认并入结果 → 剩余积压与下一步」组织。提交号、分支名、完整 SHA、路径+稳定版本标签可放在末尾的「同步信息」小节，不要让技术附注取代人类结论。

普通聊天在对话里给出完整、连续、易读的内容；大型异步报告、长主控窗口交接或确有截断风险时，才改用 Markdown 文件+链接/分份。不得把一轮普通对话强行缩成十行入口。

### 新窗口重新读规范，不靠旧窗口记忆

每次新开可写云端窗口，都重新阅读 README、云端衔接提示词、七范式、主页路径D、可读性规范和本轮相关权威文件，并核对当前公共主库与未合并改动；不得假定前一个窗口已经读过或记得。技术交接与人类对话记录分开：完整聊天原文仍按项目约定由自然人保存在 Obsidian。
