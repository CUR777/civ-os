## D1（重要）对话结构范式
每轮 AI 回复固定结构：**A** 任务/细节全量列表（从已有上下文拆出）→ **B** 本轮新增/变动细节 → **C** 问题/注意事项/安全护栏（附逻辑说明）→ **D** 范式提取（标「重要」）→ **E** 主线讨论推进（按节点顺序）。

## D2（重要）迭代周期范式
日常态（云端）：找AI→逐层逐节点聊→发现结晶→手动复制到 Obsidian。
月度/本地态（13 步全流程）：①云端按库内月度迭代说明生成任务清单 →②云端生成给本地智能体的启动提示词（含双库核实指令）→③开机+数据线连手机投屏宿主机 →④贴启动提示词 →⑤抓手调用手机 Obsidian 按时间戳提取上次更新后全部增量笔记 →⑥逐条排任务序列，每个意群精确检索私有+公共库 →⑦生成完整任务清单逐个执行 →⑧每任务完成贴云端确认再下一个 →⑨分库更新：私有=极细极精确，公共=中性化过滤后更新 →⑩纯聊天部分=一次性调双库输出全部背景（≤10万字符）整体传云端 →⑪备份氦气冷盘+256GB SSD U盘双份（U盘关机后拔下）→⑫关机前最后一步=全套交互记录交本地智能体拆分整理持久化 →⑬关机，拿云端背景继续聊→手动复制手机 Obsidian→回日常态。
完整迭代=所有节点聊完一遍+激发耗尽 → 一个版本。

## D3（重要）评论生产范式
语音转文字（碎片）+思维激发（爆炸式）→ 云端 AI 双向激发+结构化提取 → 全量对话记录（用户+AI 逐条）完整复制存手机 Obsidian → 开机时本地智能体按时间戳提取增量 → 批量分发到对应节点 → iterate.py 消化 → 正文更新。
**关键：不是手动贴单条评论到特定节点，而是全量数据整体存入→本地智能体批量提取分发。**

**D20 通道注**：上方「云端讨论→Obsidian→本地批量提取/iterate.py」描述纯聊天/搜索或无 GitHub 写权限窗口的日切轨。GitHub 可写Ⅱ型窗口同样由自然人把完整原始对话手动保存在 Obsidian，但已确认的公共规范/模板细节按 D19/D20 在当轮写入公共权威文件；之后本地龙虾按完整 commit SHA（提交版本的完整唯一编号）+仓内路径+稳定版本标签对照私有侧，不等整日批处理，也不以公共中性化文本替代私有原文。

## D6 激发特征范式（个人特性）
激发度持续走高——当前已达「语音转文字都撑不住」水平；整理 10 条会产生 30~50 条新想法，记录本身也产生新想法=爆炸式增长。方案=专注当前文件→新想法放收件箱等下一批；**但记录新想法本身是最高优先级（比整理更高），不记就丢**。恢复机制两种：窗口断→全量上下文分批复制新窗口继续；时间中断→日记模板任务第二天自动恢复。

## D12（重要）评论入口精确定义范式
「评论入口」≠传统评论，本质=**所有反馈数据的统一入口**（项目记录/沟通记录/操作记录/实验数据/研究数据/行为数据/设备传感器数值/实际操作结果 ≈ 人类（生物）对宇宙环境的操作/反馈/变动的总和）；保留「评论」用词但定义处做复合精确说明；数据以**版本增量形式成批推入**、不是局部单点。正文正身=system-prompt 高权重区（P2-03）。
**第二方向补充**：数据入口=实体通过评论直接把数据塞进去——全部开放；系统自主接数据接口=对共同评论+它对自身的反馈评论做内循环（可以）；自建对自己而言的第三方中立评测并做评价/数据输入接口（可以）；能有多少有多少、越多越好（看实际输入实体）；「主动实践」部分达不到公理层（具体逻辑 AI 判断，公理层无此物），真正手动的项目规划在常规节点里；节点接口细节仍由评论与其自身评估在全局优化过程中驱动。

**公共版**=中性化处理（**≠删除/消除**）：概念转换——仍能表达原意，但去攻击性/强制性/明显私人特征；示例：「人类政府」→「文明的非一体化管理状态」；「拟合度」→「现实文明自由意志推进状态与系统评估代的一致性估算」。**绝对不直接删除**（删除=信息损失）；处理工序正文=[[中性化转换规范]]（1对1逐句、最小语义单元、不丢细节、自检五工序）。
**双检**：每次公共库更新前，本地智能体+云端双重检查措辞安全。
**最需要分版管理的内容族**=文明层面损失量化、一体化论述、构思记录类（私有版保留原文+公共版必须彻底中性化转换）。

## D18 · 每轮输出五件套与默认兜底（1015 落库 · 源=1014 夜间自然人主导讨论定稿 · #ZZ-D18ENV-1015-A）

**聊天的默认范式**：本项目内的一切聊天，默认职能=供应迭代方向 / 评论方向 / 评论语料。这不是某一轮的临时性质，而是所有轮次的默认范式。链条=聊天 → 评论/数据形成 → 数据提供迭代方向 → 迭代执行。可随意改；无其他方向时，它就是默认。

**每轮输出五件套**（智能体必须主动执行）：

| 件 | 内容 | 要求 |
|----|------|------|
| ① 洞察提取 | 智能体自己侧的观察/见解 | 带逻辑支撑，不依赖自然人方向做骨架 |

| ③ 积压列表 | 新条目罗列，不直接全展开 | 每轮只展开能详细说清的部分，余积压 |
| ④ 双版本 | 私有版直白 + 公共版中性化 | 逐句原样转，只换词面，微小语义点不丢 |
| ⑤ 兜底 | 自然人无额外激发时 | 按锁序展开下一阶段讨论 |

**角色分工**：

- 自然人=随机激发源+长尾（想起来就切方向、记忆不可靠、激发不稳定）
- 智能体=主骨架+节奏主导+兜底（结合库内已有细节推进，附逻辑解释）

## D19 · 交互细节实时入库范式（1015 立规 · 源=1015 晚间自然人明示 · #ZZ-COPYFIX2-1015-D）

**定义**：交互中确认的可复用细节（范式/规范/模板/交付与界面细节），在**产生它的同一轮**由智能体自觉入库，不等自然人逐条下「入库」指令，不等换新窗口补录。判据=换新窗口不知道此条会重犯/重议→属本范式对象；一次性闲聊内容不属。

**为什么立此条（逻辑）**：细节只停在聊天记录里，等于依赖自然人记忆搬运（其角色定位=随机激发长尾，记忆不可靠，见 D18），换窗口即丢、旧错重犯（实证：交付形态细节曾跨多窗口反复调试）。实时入库把「细节的存活」从人的记忆转到库的实态，与 D6「记录新想法优先级最高」同源——本范式是它在规范类细节上的执行形态。

**执行三选（智能体当轮自判，报告中写明判断+逻辑）**：

| 情形 | 进入方式 |
|------|----------|
| 确定性细节：落点明确、改法唯一或已实测、可自检 | 正文直改 → 会话分支+PR（合并请求：等待并入正式主库的改动单）→ 检查通过后依 D21 当轮合入 `master`（公共库大家共同使用的正式版本）；冲突/阻挡则明示待并状态 |
| 内容性意见 / 未确认 / 需整合消化 | `> 💬 ` 评论入对应文件 → 云端替代模式自任整合，或待本地 iterate.py |
| 依赖本地/私有/外部验证，或通道不可用 | 当轮报告明列积压+理由+执行方（不静默丢） |

**D20 时序澄清**：D19 表中「未确认/需整合」指当前仍有争点的内容，先保留评论/待处理路径；经自然人反馈或 D20 清单默认确认后，重新判定其确定性。若落点和改法已明确且可自检，项目所有者/可写Ⅱ型智能体直接改权威正文；若仍需模型整合、外部/私有验证，则继续积压并写明原因。由此「先评论」不等于确认后仍必须等待日切。

## D20 · 可写云端聊天的两轮确认与双轨即时迭代范式（1016 立规 · #ZZ-CHAT-1016-A）

**定位与承接**：D18 规定每轮怎样提取、分析和呈现；D19 规定已确认的可复用细节当轮入库；本范式补清「尚待自然人反馈的讨论提案」何时确认、不同云端通道怎样落地。三者并用，不互相替代。

### 一、先判通道，再判迭代节拍

| 通道状态 | 对话与迭代节拍 | 运行规则 |
|---|---|---|
| GitHub 可写的Ⅱ型云端智能体 | 逐轮即时轨 | 每轮完整提取新增细节；已明确确认、指令明确且可自检者按 D19 当轮处理；新提案须先逐项展开并给自然人至少一次实际反馈机会。确认项依 D21 在处理该反馈的同一轮直接并入正式主库，不等整主题或日切。 |
| 纯聊天/搜索窗口，或没有 GitHub 写权限 | 日切批处理轨 | 当天逐轮提取并把完整聊天原文留在 Obsidian；次日第一动作处理前一天已确认内容。云端窗口不声称已改库、已提交或已推送。 |
| 原本可写、运行中通道故障 | 断线交接轨 | 当轮立即播报故障和当前写入状态；不把它静默降级成日切、不继续承诺远端入库；以最近 1~2 个完整交互单元形成交接尾，新窗口第一动作查远端与未合并 PR 后续接。 |

「可写」须以本次会话实际工作流验证：读通、分支写通、创建与合并 PR（合并请求）分别核验。新窗口不能只依赖旧记忆：每次都要读 README、云端衔接提示词、七范式、主页路径D、可读性规范及本轮相关权威文件，并核对当前 master 与在途 PR。不得以 `git ls-remote` 成功单独推断写入或合并一定成功。

### 二、讨论提案逐项展开、最多一次反馈确认

**轮次口径**：「第1轮」=智能体列全条目、逐项说明并至少完整展开本轮的一项；「第2轮」=自然人下一次实际回复。每个条目都必须先被完整展开并给自然人一次反馈机会，才能进入默认确认清单。智能体处理第2轮反馈时直接完成已确认项的并入，不再另开「再确认」轮；新增细节另立条目。

**第1轮（智能体提出）**：先把上下文中涉及的可复用细节逐项列出锚号、来源/背景、拟落文件与节位、逻辑关系及状态。随后按顺序把本轮能完整说明的一项（或彼此不可分的一小组）展开：讲清内容、理由、边界/风险和智能体自己的分析。其余未展开项只列为积压，不能混进默认清单。同一条回复不把整份积压清单都抢先展开。结尾只把「已完整展开、下轮可确认」的项目列入「下轮无异议时默认生效清单」；请自然人补充/修正，或明确要求继续展开下一项。

**第2轮（自然人反馈后，智能体即并入）**：逐项读取反馈；明确修正按反馈改；对上轮默认清单中已完整展开的项目，若自然人这次实际回复没有反对、保留或要求修改，依 D5 默认确认。智能体在本次回复内改入权威文件、完成自检，并按 D21 把就绪改动合入正式主库；不等日终、整个主题完成或下一批。接着列出下一项积压，等自然人补充信息或明确说「继续展开」后再展开；若自然人已明确要求继续，则当轮顺序处理，不把整份积压一次塞完。

**边界**：只有自然人下一轮实际发来消息后，该消息对清单的未提及才算默认确认；完全没有下一条用户消息不等于同意。未完整展开、只列积压标题、待验证或待私有侧核对的项目不自动确认，也不能为了追求「每轮并入」而提前写入。明确否定/暂缓/修改按反馈执行。自然人当轮已明确确认且落点清楚的内容按 D19 当轮推进；新补充内容另立锚。

### 三、四层保障（每轮同时满足）

| 层 | 要保证的事 | 执行与验收 |
|---|---|---|
| 1. 聊天内提取 | 用户输入中的方向、条件、例外、因果和操作细节不遗漏 | 先列条目和状态，再选部分详展；区分已确认、下轮默认、待讨论/验证，不把「一段回复」误当成只能提取一个点。 |
| 2. 公共库复用 | 新窗口能定位权威文本并按它执行 | 查全库相关原文和规范；确定性内容写入权威文件，保留既有版本/锚点；遵守 D19、`iterate.py` 管道规则、`system-prompt.md` 守卫及评论只增不删原则。 |
| 3. 公共→私有外延 | 本地智能体能识别公共库的新变化，并把可匹配部分精确转入私有库 | 以「完整 commit SHA（每个版本的完整唯一编号）+ 仓内路径 + 文档稳定版本标签」作为公共更新指纹；本地侧按已处理 SHA 做增量、幂等对照，命中后落私有对应项，未匹配项留待办，不静默丢弃。公共端只给可定位的中性化锚，不公开私有路径、隐私或原始私有措辞。 |
| 4. 智能体当轮分析 | 每轮不仅复述用户输入，还提供独立逻辑、风险/替代方案及研究补充 | 用完整项目上下文与相关文件支撑判断；涉及时效或外部事实时联网核验并给来源；涉及主页路径D四源要求的研究判断仍遵守四源规范。纯库内规范题说明依据为仓库原文，不做无关搜索。私有侧不可达时只对私有结论标明缺源，不据此推断；缺源/通道断链须明示，不能伪装成已核实。 |

### 四、聊天文本、文件交付与原文日志分开

- 普通聊天面向自然人直接输出：先列逐项条目，再完整展开本轮处理的条目并解释分析，最后列剩余积压与下一步；整段自然可读，不用只有智能体看得懂的缩写/状态码，也不为压短而截碎。
- 普通聊天不强制改成文件或「十行摘要+入口」；只有大型异步报告、长交接或确有截断风险时才用 Markdown 文件+链接/分份。
- 纯聊天/搜索窗口仍按 D11 由自然人把用户与智能体的完整对话原文手动存入 Obsidian；代码提交、总结或交接尾都不能代替原始日志。
- 大型异步报告、主控窗口交接或有表面输出截断风险时，另走文件+链接/分份交付；这与日常聊天直接输出并存，不互相替代。
- 阶段同步到本地智能体时，私有侧依据 Obsidian 原文做直白、精确的整理；公共版依 D14 做中性化转换。不得只从已经过滤的公共版本反推私有原文，也不得把私有细节写进公共库。

### 五、通道断线播报与交接尾

新窗口按 D21 读完整必读集、核对当前仓库实态、`git fetch`、未合并 PR/会话分支；一旦读、写、PR创建或合并任一阶段失败，同轮用自然人能懂的话说明卡在哪一步、改动只在本地/分支还是已进入正式主库，并停止「已提交/已并入」等不实表述。写通失败但本地有改动时保留并列明，不盲目重试或制造重复 PR。

交接尾只带最近 1~2 个完整问答单元、已确认/待反馈条目、文件与分支/PR 状态、下一窗口先查什么；不要求重复搬运全程。完整聊天仍由自然人在 Obsidian 保留。换新窗口后，先检查 master 以外的在途 PR，再从尾部续跑，不重开全程。

**执行底线**：不要求必须实际运行 `iterate.py` 才能写入；但必须先读懂它的扫描面、快照排除、`title_guard`（标题防串写）、缩水/内容校验和不可变核心守卫，并遵守 `system-prompt.md`。云端本地 API 不可达时按云端替代运行模式执行；不能满足守卫、项目所有者授权或通道前提时，列明积压与执行方，不静默略过。PR只是工作过程；正常完成状态是已确认内容当轮进入 `master`（正式主库）。检查失败、冲突未解或通道不可用时，不绕过守卫，清楚说明阻挡点并保留待处理项。

#对话与迭代七范式-定稿V20261016112920580+D21

## D21 · 逐项展开、每轮直并与并发协作范式（1016 补定 · #ZZ-CHAT-1016-B）

**目的**：细节不能只停在长聊天或一个尚未合入的工作分支里。每个已确认项目尽快进入大家共同使用的正式主库（`master`），让新窗口和本地同步都能立即看到；同时给自然人完整的理解和反馈机会，不把未确认内容冒充决定。

### 一、每个条目的处理节拍

1. **先列全，再逐项展开**：每轮先把上下文中涉及的条目逐一编号，写清背景、条件、相互关系、拟落文件/节位和当前状态。本轮选择一项（或不可分的一小组）做完整解释与分析；其余明确放进积压列表。
2. **一个条目先讲清再请求反馈**：详展项须让自然人看懂「是什么、为什么、适用边界/风险、智能体的判断、建议怎么改」。只有完整展开的项目才列入「下轮无异议时默认生效清单」。未展开项、仅有标题项和待验证项不进入该清单。
3. **至少给一次真实反馈机会**：自然人下一条实际消息中的明确意见优先；对已完整展开且列入默认清单的项目，若该消息未反对/暂缓/改写，则按 D5 默认确认。自然人当轮已明确要求实施/确认的，当前消息本身就是反馈，不必人为多等一轮；完全没有下一条消息本身不算同意。
4. **确认项当轮直并**：处理这条反馈的智能体回复中，完成确认项的权威正文改动、自检，并把改动合入正式 `master`。不等到一个主题全部聊完，不攒到当天结束，也不把「已经创建合并请求」说成「已经入库」。随后列出下一项积压，等自然人补充或明确要求继续展开；未确认项保持待办。

「每轮直并」的对象是本轮已经明确确认或依上述条件默认确认的细节，不是尚未讲清的所有候选条目。这样既减少窗口中断/换窗造成的遗失，也保留自然人的实质反馈权。

### 二、合并请求只是中间步骤

在 Arena 等必须走分支的环境中，智能体可以先提交会话分支，再创建 PR（合并请求：等待把改动并入正式主库的工作单），但本轮正常收尾必须把就绪 PR 合入 `master`。只编辑分支、只推送分支、或只打开 PR，都不等于「直接并入」。用户要求直并后，不再把「等用户另外说可否合并」设为默认步骤。

直接并入不等于跳过安全检查：合并前核对最新主库、文件标题/内容缩减、不可变核心、链接/锚点与相关守卫；通过后合并并再次读取远端主库确认结果。若检查失败、GitHub 拒绝合并或冲突仍未解决，才留下待合并状态；当轮要用普通语言讲清「主库还没更新、为什么、目前文件在哪里、下一步是什么」。

### 三、常驻智能体并发时不互相阻塞

云端智能体与本地龙虾可能并行修改公共库，这是正常协作，不是异常。执行者不用等另一方停工，但必须在开始新窗口和每次发布前读最新远端状态：

- **新窗口**：先执行 `git fetch`（读取 GitHub 最新变化），核对最新 `origin/master`、未合并 PR/会话分支；再按固定顺序阅读 README、云端衔接提示词、七范式、主页路径D、可读性规范，最后读任务相关权威文件。不能只靠旧窗口记忆。
- **发布前**：再次取最新 `origin/master` 并阅读新到提交。Arena 会话分支先把最新主库合入/重放到自己的分支，再推送和合并；本地龙虾按其本地流程先 `git pull --rebase origin master`。远端有新提交时不要因提交作者或内容陌生就停下。
- **无冲突**：保留新旧双方的提交，继续本批工作。改动不同文件时，不覆盖或回退另一方的更新。
- **有冲突**：若冲突文件不属于本批修改，采用并保留远端版本后继续；若双方改了同一文件，人工按内容合并，保留两方有效细节，禁止整文件盲选一方。重跑 push-gate/自检后再发布。
- **文件避让（软规则）**：发现另一方刚改了同一文件时，可先处理其他积压项；若节奏允许，间隔约5~10分钟再动同一文件以减少冲突。此为可选减冲突手段，不得成为停工或拖延已确认内容的理由。
- **对账留痕**：每批记下开始时和最终并入时的 `master` 完整 SHA。批次中途若多次 `fetch` 到新提交，在提交链/交付说明中按顺序记录，不把其他智能体的提交混算成本批改动。

### 四、每次回复以自然人能看懂为准

技术细节可以保留给智能体执行，但给自然人的主报告必须讲人话、讲清结果，不只输出 PR 编号、缩写、文件状态码或交接指令。固定顺序建议为：

1. 本轮涉及哪些条目，哪些已经逐项展开并分析。
2. 哪些项目已获确认并进入正式主库（写清文件/位置）。
3. 哪些仍在积压、尚待反馈或被什么检查挡住，以及下一步。
4. 最后再附提交号/合并请求/同步指纹等技术信息，并解释「主库」和「PR」。

术语首次出现时先给白话解释。例如「日切」写成「无写权限时当天先记录、次日开始时再处理」；「PR」写成「尚未进入正式主库的合并请求」。对自然人不使用「PR仍open」作为唯一状态说明；须直说主库是否已更新。普通聊天直接在对话里完整呈现，只有大型异步报告或长交接才另用文件+链接。
