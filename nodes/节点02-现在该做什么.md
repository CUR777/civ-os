# 文明OS

## 节点2：现在该做什么


【当前阶段·已实现】

基于节点1的关键问题，当前最优行动是：

1. 完成本框架的技术搭建（迭代脚本 + 系统提示词 + 版本控制）
2. 运行首次迭代测试，验证公理执行效果
3. 推送至GitHub公共仓库，开始接收外部反馈
4. 后续每一轮迭代：收集评论 → 智能体整理 → 产出新版本 → 发布
5. 框架稳定后，原作者退出维护角色，仅以评论者身份参与

### 当前实现状态精确描述（v0.2.2基准）

| 维度 | 状态 |
|------|------|
| 实现形态 | 纯文本markdown框架 + Python迭代脚本（iterate.py） |
| 模型 | 单一本地模型（Qwen 3.8 flash 125B FP4，sglang部署） |
| 迭代能力 | 接收💬格式评论 → 提取逻辑 → 整合 → git commit → GitHub push，全程约60~95秒自动完成（含模型推理、校验、格式后处理、commit、push） |
| 版本控制 | Git + GitHub |
| 编码辅助 | Aider（v0.86.2），已安装可用，但当前自动迭代管道（iterate.py）不依赖Aider运行。Aider的实际用途是辅助修改iterate.py和system-prompt.md等脚本文件本身，不参与正常的内容迭代流程。 |
| 用户交互入口 | 主入口为「文明OS-主页.md」，用户通过主页中的双向链接进入各节点文件，在对应节点内以 `> 💬 ` 格式添加评论；迭代脚本扫描所有节点文件中的评论标记并统一处理。 |

**未实现组件（按优先级排列）：** 交叉核验（节点5）、模型自动选择/Optimizer Agent（节点11）、积分经济（节点8）、用户认证体系、分布式节点网络（节点13）、多模态输入、数字警察自动化（节点12中期层）。

**生态依赖与可持续性设计：** 项目自举阶段依赖外部接盘者（企业/机构/社区）接手持续维护，原作者个人算力与时间不足以支撑长期运营。此约束是节点15"Fork合法性"与"多版本共存"架构设计的直接动因——系统从架构层面不依赖单一维护者，任何实体均可fork后独立演化，主仓库为参考实现而非唯一合法实现。

### 分层更新频率设计

框架采用分层更新频率机制，更新频率与节点层级成反比：

| 层级 | 示例 | 更新频率 | 理由 |
|------|------|----------|------|
| 底层（实现层） | 技术栈、脚本、模型选型、具体参数 | 高（每轮迭代均可调整） | 具体实现随技术发展快速演进，需高频适配 |
| 中层（结构层） | 节点划分、流程步骤、交互协议 | 中（数轮迭代后评估调整） | 结构变更影响面大，需积累足够反馈后再动 |
| 顶层（原则层） | 公理、元流程、全局目标 | 极低（仅在公理自身逻辑出现矛盾时触发） | 顶层是系统稳定性的锚点，频繁变动将导致飞轮失稳 |

设计原则：底层的高频迭代为顶层提供演化素材；顶层的稳定性为底层迭代提供方向约束。二者构成"快变量驱动慢变量"的耦合关系，确保系统既保持适应性又不丧失一致性。

### 子节点02-01：iterate.py管道技术完整规范

#### 核心配置

| 参数 | 值 |
|------|------|
| MODEL | pennyroyal |
| API端点 | `http://127.0.0.1:8001/v1/chat/completions` |
| 协议 | OpenAI兼容，无鉴权 |

#### 处理流程（单轮迭代）

```
扫描主页 + nodes/目录
  → 识别行首 "^> 💬 " 评论
  → 备份当前文件
  → 调用模型（将评论+原文送入system-prompt）
  → 校验输出
  → 格式后处理
  → git commit
  → git push
```

#### 校验机制

- **主页校验**：确认公理Ⅰ、公理Ⅱ、公理Ⅲ及元流程区全部在位且文字未被篡改
- **节点校验**：确认每个节点文件有内容且不为空
- 校验失败 → 回滚至备份，本轮迭代中止并报告错误

#### 格式后处理

- `lstrip('\n')`：去除文件首部多余空行，确保首行直接为标题
- `rstrip('\n') + '\n'`：规范文件末尾恰好保留一个换行符

#### 分段机制

- 触发条件：单文件超过200KB
- 切分策略：按节点边界切分，单段上限150KB，不截断任何节点内容
- 目的：适配模型上下文窗口限制，避免超长输入导致推理质量下降

#### 版本号规则

- **patch位**（x.y.z 的 z）：每次有实质内容变更的迭代后自动+1
- **minor位**（x.y.z 的 y）：仅当评论明确指定时才变更
- **major位**（x.y.z 的 x）：仅当评论明确指定时才变更
- 空转迭代（无实质内容变更）不递增版本号

#### 当前性能指标

| 指标 | 数值 |
|------|------|
| 单轮总耗时 | 约60~95秒 |
| 耗时构成 | 模型推理 + 校验 + 格式后处理 + commit + push |
| 并发能力 | 单线程串行（当前设计） |

### 子节点02-02：GitHub仓库结构与三条参与路径

#### 仓库信息

- **地址**：https://github.com/CUR777/civ-os
- **可见性**：公开
- **协议**：MIT

#### 文件结构

```
civ-os/
├── 文明OS-主页.md          # 主入口，含双向链接导航
├── nodes/                  # 16个顶层节点 + 子节点目录
│   ├── 节点01-*.md
│   ├── 节点02-*.md
│   ├── 节点02-01-*.md     # 子节点
│   ├── 节点02-02-*.md
│   ├── 节点02-03-*.md
│   └── ...
├── archive/                # 历史快照（按版本归档）
├── system-prompt.md        # 智能体系统提示词
├── iterate.py              # 迭代管道脚本
└── README.md               # 项目说明
```

#### 路径A：AI智能体参与

1. 读取 `文明OS-主页.md` 了解全局结构
2. 进入 `nodes/` 目录读取目标节点
3. 在对应节点文件内插入行首 `> 💬 ` 格式评论
4. 执行 `iterate.py` 触发迭代

#### 路径B：Obsidian本地编辑

1. `git clone` 仓库
2. 在Obsidian中打开 `civ-os/` 目录为独立库（Vault）
3. 通过双向链接导航，悬停预览节点内容
4. 编辑节点文件，添加 `> 💬 ` 评论
5. 告知智能体执行迭代（或自行运行 `iterate.py`）

**注意事项：**
- 仅开启局部图谱（右键节点 → 局部图谱），不开启全局图谱（文件数超过10万时全局图谱会导致严重卡顿）
- 双向链接 `[[...]]` 在GitHub网页端显示为普通文本，悬停预览为Obsidian特有功能

#### 路径C：GitHub网页参与

1. 在GitHub网页浏览 `nodes/` 目录
2. Fork仓库至个人账号
3. 本地clone后编辑节点、添加评论
4. 运行 `iterate.py` 完成迭代
5. 向主仓库提交Pull Request

#### 核心原则：append-only

- 禁止 `git force push`
- 禁止 `git rebase`（改写历史）
- 所有历史commit永久保留，确保演化轨迹可审计、可回溯

### 子节点02-03：待实现功能优先级清单

| 优先级 | 功能 | 时间窗口 | 前置条件 |
|--------|------|----------|----------|
| 1 | 导航区旧提示行"鼠标悬停预览"加Obsidian限定词 | 近期 | 无（纯文本修改） |
| 2 | Hypothesis注释系统集成（用户评论私有化） | 中期·条件性 | 依赖外部服务部署 |
| 3 | 双repo方案（公共展示 + 私有反馈） | 中期·条件性 | 依赖GitHub账号配置和脚本升级 |
| 4 | 交叉核验实施（节点5） | 中期·条件性 | 需要多个可用模型，当前单模型环境不具备 |
| 5 | Optimizer Agent（硬件自动匹配模型，节点11） | 后期·条件性 | 依赖分布式节点加入 |
| 6 | 积分经济体系（节点8） | 后期·条件性 | 依赖文明OS底层需求规模化 |

**优先级排序逻辑：** 按"实现成本 × 阻塞程度"综合排序。优先级1为即时可完成的文本修正；优先级2~4为中期功能，各有明确的外部依赖；优先级5~6为远期架构目标，依赖系统规模达到临界点后方可启动。

**推进原则：** 每项功能在条件成熟时自动进入迭代队列，无需等待前序功能全部完成。条件性功能若长期不满足前置条件，保持"等待进一步技术发展后重新评估"状态，不关闭、不删除。
