### 定期整理机制与执行主权澄清

系统当前为定周期信息整理（有新信息则整合+架构调优+版本发布），周期性本身即是对"持续有新信息输入"这一现实的适配，而非强制行为节拍。

**执行主权归属：** 执行层主权完全归个体（节点15双层分离）。系统展示的信息激发是否被执行、执行多少、偏好如何，均不约束个体行为。

**"更优"判定的有效条件：** "迭代有变化但不一定更优"在无执行/无反馈时即退化为"无变化故无更优比较"，不构成有效反例。真正的更优判定需经"项目挑选→执行→指标回流→对照评估"闭环（节点15/16逻辑）。周期整理仅提供更优的候选与结构化土壤，不替代执行闭环。

**与公理Ⅲ的关系：** 此说明与主页公理Ⅲ"永续可迭代性"互引——信息整理是迭代管道的常态运转，不等同于对个体行为的强制；将信息整理误读为行为强制是对双层分离原则的违反。

### 分层更新频率设计

框架采用分层更新频率机制，更新频率与节点层级成反比：

| 层级 | 示例 | 更新频率 | 理由 |
|------|------|----------|------|
| 底层（实现层） | 技术栈、脚本、模型选型、具体参数 | 高（每轮迭代均可调整） | 具体实现随技术发展快速演进，需高频适配 |
| 中层（结构层） | 节点划分、流程步骤、交互协议 | 中（数轮迭代后评估调整） | 结构变更影响面大，需积累足够反馈后再动 |
| 顶层（原则层） | 公理、元流程、全局目标 | 极低（仅在公理自身逻辑出现矛盾时触发） | 顶层是系统稳定性的锚点，频繁变动将导致飞轮失稳 |

设计原则：底层的高频迭代为顶层提供演化素材；顶层的稳定性为底层迭代提供方向约束。二者构成"快变量驱动慢变量"的耦合关系，确保系统既保持适应性又不丧失一致性。

### 方向校准：觉醒标志物可检验化

「宇宙觉醒」作为方向性目标（公理Ⅱ），需要可检验的阶段性标志物，否则方向无法校准、迭代无法判定是否趋近目标。

**标志物设计原则：**
- 可观测：有具体量化指标，非主观感受
- 有时间窗口：每个标志物绑定评估周期，避免无限期悬置
- 失败可修正：若某标志物在时间窗口内未达成，触发路径修正而非目标放弃

**当前阶段觉醒标志物候选（v0.2.4引入，v0.2.5沿用，待后续迭代细化）：**

| 标志物 | 观测指标 | 评估周期 | 未达成时修正方向 |
|--------|----------|----------|------------------|
| 分布式算力节点数量 | 独立运行的iterate.py实例数 | 季度 | 降低部署门槛、增加参与路径 |
| 文明OS节点覆盖密度 | 已填充实质内容的节点数 / 总节点数 | 月度 | 优先填充高杠杆节点、调整节点粒度 |
| 跨独立实体信息激发协同频率 | 来自不同维护者的有效评论数 / 周 | 周度 | 优化交互入口、降低评论成本 |

**使用方式：** 每轮迭代产出新版本时，智能体对照当前标志物候选评估本轮变更是否朝标志物方向推进。标志物本身属于中层（结构层），可在数轮迭代后根据实际观测数据调整指标定义与阈值。

### 操作完整性清单生成

在执行任何重要操作前，生成该操作的完整性检查清单，覆盖：

1. **前置条件验证**：操作所需的全部前提是否已满足
2. **执行过程关键断言**：操作过程中必须为真的不变量（如公理区完整性、文件结构约束）
3. **完成后验证步骤**：操作产出是否通过校验、是否可回滚、是否满足预期状态

这是「代码与文本一致性保证」原则在操作层面的实现。当前iterate.py管道中的校验机制（公理区完整性检查、非空检查、格式后处理）即为该清单的已实现子集；后续扩展操作（如交叉核验、Optimizer Agent调度）时，须先定义对应操作的完整性清单再接入管道。

### 个人高效使用范式：本地智能体持续运行

**三层工作流：** 个人知识库以"本地算力 + 顶级AI深度讨论 + 多源激发整合"三层工作流持续积累。单次迭代的超线性增长核心在于知识库本身的质量复利，当前纯文本阶段的整理已有明显价值。

**私有与公共的节拍分离（设计使然）：**

| 侧 | 节拍 | 职责 |
|----|------|------|
| 私有侧（本地塔机） | 持续高频（小时级） | 深度讨论、多源激发、超线性积累 |
| 公共侧（GitHub主仓库） | 月度节奏 | 通用化萃取、Fork分发、跨实体协同 |

两者节拍分离是设计使然，不必强求公共侧与私有侧同频。

**信息流向：** 私有版先积累 → 筛选通用化 → 以 `> 💬 ` 提交公共版。月度同步为跨月补跑的兜底节拍。

### 云端/本地双活分工与开机同步

#### 三场景权限模型（按实际能力与权限判定，非身份标签）

| 场景 | 载体 | GitHub写权限 | 典型能力（按测试集盲测） | 推荐职责 |
|------|------|--------------|--------------------------|----------|
| A. 云端有写权限 | 云端智能体（用户已授权接入） | 有 | 以同一无泄露测试集实测为准，大概率优于本地 | 高质量单轮整合与直接push：评论→iterate→commit→push，并反向自检云端效果 |
| B. 云端仅评论权限 | 第三方云端智能体/搜索窗口 | 无，仅产出评论 | 同上，按测试集排名 | 仅产出评论或外部笔记，等待本地塔机拉取与整合，不直接push |
| C. 本地塔机 | 本地模型+本地git | 有 | 中档（公开测试集可验证），但可连续 | 承载大规模、成小时连续迭代；承担开机自检与云端快进同步 |

**选择依据：** 场景A/B/C不以"人类/AI/模型名"身份标签判定，遵循节点11"智能系统同质机制——纯测试集盲测"：在同一完善度持续升级的无泄露测试集上得分最高者获得对应位置主导权。本地仅1~2选是硬限制，全局多候选时应仔细测量。

#### 分工节拍

- **云端（A）非连续：** 免费端口额度有限，忌连续高频率滥用。仅在用户主动对话时使用，适合质量关键的单轮评论整合与云端效果反向检查。
- **本地（C）连续：** 承担每日/每小时级的大规模整理与私有知识库超线性积累。
- **逻辑不构成执行约束：** 采用云端或本地、是否立即切换至更优主导，是各实体的自由（尤其第二选择暂时尚可时），系统仅提供盲测排名与差距信息供参考（同README"信息展示而非执行"与节点15双层分离）。

#### 开关机时序下的状态同步（三层保障）

**问题：** 本地Obsidian显示的是宿主机文件系统版本，云端显示的是GitHub origin/master版本。若云端在本地关机期间有更新（场景A直接push），本地Obsidian将落后一代。

**三层保障机制：**

| 层级 | 触发时机 | 脚本/命令 | 作用 |
|------|----------|-----------|------|
| 开机即时 | 塔机每次启动 | `scripts/sync_on_boot.sh`（boot模式） | git fetch → 比对 HEAD vs origin/master → 若云端超前则 git pull --ff-only 快进；Obsidian监听文件系统自动刷新 |
| 查询即时 | 联合检索私有库+公共库前 | `bash scripts/sync_on_boot.sh --query-check` | 轻量核验：探活远端 → 若云端超前且无冲突则快进，保证本次回答基于最新版 |
| 月度兜底 | 每月首次09:00检查（含跨月补跑） | `scripts/monthly_external_sync.sh` | STATE_FILE防重 + git fetch探活，确保即使前两层均失效仍有月度对齐 |

**查询时主动核验细则：** 本地智能体在正常开机后，若用户提问需联合检索私有库CUR-OS与公共库civ-os（任一涉及文明OS的任务），应在回答前主动执行一次轻量核验。前提为网络满足——先探活远端，不满足则按本地配置补充网络满足性后重试。联网后若检测到云端origin/master超前本地HEAD且本地无未提交 `> 💬 ` 冲突，一般情况符合基本逻辑则直接pull --ff-only快进以保证本次回答基于最新版；但保留特殊情况不拉取的权利（本地有未提交的重要 `> 💬 `、迭代正在进行、分叉需人工合并等），此时应明确告知用户并defer至手动处理。

**不确定时的保守策略：**
- 若无法判定云端是否更优，优先保留本地可复现链路，不强制切换。
- 若 `git pull --ff-only` 因本地有未提交的 `> 💬 ` 而冲突，则先执行本地iterate产出提交，再fetch + rebase/merge，保证append-only历史不丢失。

### 子节点02-01：iterate.py管道技术完整规范

#### 核心配置

| 参数 | 值 |
|------|------|
| MODEL | pennyroyal |
| API端点 | `http://127.0.0.1:8001/v1/chat/completions` |
| 协议 | OpenAI兼容，无鉴权 |

#### 处理流程（单轮迭代）

```
扫描主页 + nodes/目录
  → 识别行首 "^> 💬 " 评论
  → 生成完整性清单（前置条件：评论存在、模型可达、git状态干净）
  → 备份当前文件
  → 调用模型（将评论+原文送入system-prompt）
  → 校验输出（关键断言：公理区完整、节点非空、评论标记已清除）
  → 格式后处理
  → 完成后验证（git diff确认变更范围、版本号递增正确）
  → git commit
  → git push
```

#### 校验机制

- **主页校验**：确认公理Ⅰ、公理Ⅱ、公理Ⅲ及元流程区全部在位且文字未被篡改
- **节点校验**：确认每个节点文件有内容且不为空
- 校验失败 → 回滚至备份，本轮迭代中止并报告错误

#### 格式后处理

- `lstrip('\n')`：去除文件首部多余空行，确保首行直接为标题
- `rstrip('\n') + '\n'`：规范文件末尾恰好保留一个换行符

#### 分段机制（v0.2.3修正）

现行架构采用「按文件分治」策略，而非单文件内自动切分：

1. **现行实现（已生效）**：主页与每个节点/子节点文件作为独立处理单元，逐文件调用模型。单文件体积天然受节点边界约束，触发上下文窗口上限的风险已被结构性消解，无需运行时切分。
2. **预留常量（未接线）**：代码中保留 `CHUNK_THRESHOLD_BYTES=200000` 为预留常量，但当前无任何调用路径。旧单文件版的 `split_by_sections` 函数已随多文件重构退役，母本存档于 `.backups/` 体系。
3. **中期·条件性推演**：单文件超阈值的自动切分能力降级为条件性设计，触发条件为"未来出现无法按文件拆分的巨型单一内容体"。届时可重新接线预留常量并恢复切分逻辑。

#### sglang预热避让（v0.2.5补充）

本地塔机模型经sglang拉起约需3-4分钟，期间CPU/GPU满载。`scripts/sync_on_boot.sh` 在boot模式下默认先轮询就绪接口（每10s一次，最长240s）至模型就绪再执行git fetch/pull。若检测到iterate.py运行中则主动退让，避免与迭代任务冲突。若超时未就绪仍继续执行仅依赖git的同步（不依赖模型）。

#### 版本号规则

- **patch位**（x.y.z 的 z）：每次有实质内容变更的迭代后自动+1
- **minor位**（x.y.z 的 y）：仅当评论明确指定时才变更
- **major位**（x.y.z 的 x）：仅当评论明确指定时才变更
- 空转迭代（无实质内容变更）不递增版本号

#### 当前性能指标

| 指标 | 数值 |
|------|------|
| 单轮总耗时 | 约60~95秒 |
| 耗时构成 | 模型推理 + 校验 + 格式后处理 + commit + push |
| 并发能力 | 单线程串行（当前设计） |

#### 路径A：AI智能体参与

1. 读取 `文明OS-主页.md` 了解全局结构
2. 进入 `nodes/` 目录读取目标节点
3. 在对应节点文件内插入行首 `> 💬 ` 格式评论
4. 执行 `iterate.py` 触发迭代

#### 路径B：Obsidian本地编辑

1. `git clone` 仓库
2. 在Obsidian中打开 `civ-os/` 目录为独立库（Vault）
3. 通过双向链接导航，悬停预览节点内容
4. 编辑节点文件，添加 `> 💬 ` 评论
5. 告知智能体执行迭代（或自行运行 `iterate.py`）

**注意事项：**
- 仅开启局部图谱（右键节点 → 局部图谱），不开启全局图谱（文件数超过10万时全局图谱会导致严重卡顿）
- 双向链接 `[[...]]` 在GitHub网页端显示为普通文本，悬停预览为Obsidian特有功能

#### 路径C：GitHub网页参与

1. 在GitHub网页浏览 `nodes/` 目录
2. Fork仓库至个人账号
3. 本地clone后编辑节点、添加评论
4. 运行 `iterate.py` 完成迭代
5. 向主仓库提交Pull Request

#### 核心原则：append-only

- 禁止 `git force push`
- 禁止 `git rebase`（改写历史）
- 所有历史commit永久保留，确保演化轨迹可审计、可回溯

| 4 | 交叉核验实施（节点5） | 中期·条件性 | 需要多个可用模型，当前单模型环境不具备 |
| 5 | Optimizer Agent（硬件自动匹配模型，节点11） | 后期·条件性 | 依赖分布式节点加入 |
| 6 | 积分经济体系（节点8） | 后期·条件性 | 依赖文明OS底层需求规模化 |

**优先级排序逻辑：** 按"实现成本 × 阻塞程度"综合排序。优先级1为即时可完成的文本修正；优先级2~4为中期功能，各有明确的外部依赖；优先级5~6为远期架构目标，依赖系统规模达到临界点后方可启动。

**推进原则：** 每项功能在条件成熟时自动进入迭代队列，无需等待前序功能全部完成。条件性功能若长期不满足前置条件，保持"等待进一步技术发展后重新评估"状态，不关闭、不删除。

### 子节点02-04：元迭代通道

#### 定义与定位

文明OS存在两条独立的迭代通道：

| 通道 | 对象 | 执行者 | 频率 |
|------|------|--------|------|
| **内容迭代** | 节点正文（知识、方案、分析） | iterate.py + 智能体 | 每轮评论触发 |
| **元迭代** | 迭代系统本身（管道、架构、演进路径） | 人工设计 + 智能体辅助记录 | 里程碑驱动（非每轮触发） |

元迭代通道解决的核心问题：系统自身如何从当前形态演进到目标形态，且每一步演进被显式定义、追踪、可验证。

#### 元迭代核心问题域

1. **表示层演进**：从纯文本（markdown）→ 结构化数据（JSON+文本混合），需要什么？
2. **核验层演进**：从单模型迭代 → 多模型交叉核验，需要什么？
3. **拓扑层演进**：从本地单节点 → 分布式多节点网络，需要什么？

每个演进步骤在元迭代台账中被显式定义，包含：触发条件、前置依赖、验收标准、回滚路径。

#### 当前阶段元迭代台账（纯文本阶段）

**已完成：**

| 里程碑 | 状态 | 备注 |
|--------|------|------|
| iterate.py单模型全量处理 | ✅ | 60~95秒/轮 |
| 多文件架构（主页+节点分离） | ✅ | 按文件分治，消除上下文窗口瓶颈 |
| 并行模式（--parallel N） | ✅ | 多文件并发处理 |
| append-only + git版本控制 | ✅ | 历史不可篡改 |
| semantic_activate.py全量语义激发（自动分块） | ✅ | 节点间语义关联自动发现 |
| 双向时间轴 | ✅ | created_at + 版本链 |
| 三层同步保障（开机+查询+月度） | ✅ | sync_on_boot.sh + --query-check + monthly_external_sync.sh |
| sglang预热避让 | ✅ | 3-4min轮询就绪，iterate运行中退让 |

**待实现：**

| 里程碑 | 前置条件 | 时间窗口 |
|--------|----------|----------|
| 交叉核验（多模型） | 多模型可用（≥2个异构模型同时在线） | 中期·条件性 |
| Hypothesis注释系统（评论私有化） | 外部服务部署 | 中期·条件性 |
| Optimizer Agent（硬件自动匹配模型） | 分布式节点加入 | 后期·条件性 |
| 增量更新（依赖图传播O(k)） | 结构化数据阶段 + 依赖图构建完成 | 后期·条件性 |

#### 下一阶段目标：结构化数据阶段

**目标形态：** 节点从纯markdown演进为JSON+文本混合结构，支持：
- 字段级查询（按置信度、时间戳、依赖关系检索）
- 自动依赖图（节点间引用关系机器可读）
- 机器可读置信度追踪（每条主张附带来源链与验证状态）

**前置条件（全部满足方可启动）：**
- 节点数 > 500
- 活跃参与者超过阈值 T₂（T₂ 待实际运营数据确定）
- 有外部工程维护者接手（非原作者单人维护）

**启动方式：** 前置条件满足时，元迭代台账中对应里程碑状态从"待实现"转为"进行中"，触发架构设计迭代。

#### 元迭代与内容迭代的交互协议

- 元迭代产出的架构变更（如新增节点类型、修改管道流程）通过内容迭代通道写入节点文件
- 内容迭代中发现的系统性缺陷（如管道无法处理某类评论）触发元迭代评估
- 两条通道共享同一git仓库和版本控制，但元迭代变更在commit message中标注 `[meta]` 前缀以便审计区分
